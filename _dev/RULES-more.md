## 2. ファイル分割（つづき）

- **1ファイルのアプリを分けるとき**（2026-10-12 に体内ダイブ・尿の旅・血管の旅・量子・電波の5本を分けた）: `_dev/tools/split-single.pl` で、CSS と、本体の JS を役割の切れ目ごとに**並び順を変えずに**切り出す（中身は変えない）。本体が `(function(){…})()` で包まれていたら包みを外し、名前をファイルをまたいで共有させる。そのとき (1) いちばん外側の `return` は書けない（`throw` とフラグにする。例: `wifi-wave/js/gl.js`）、(2) 後ろのファイルの関数を前のファイルのいちばん外側から呼ぶと動かない、(3) `top`・`name` などブラウザの名前とぶつかることがある。分けたら、**分ける前の版と同じ手順で同じ結果になるか**をくらべ（`versions/` の前の版をサーバーで開いて同じコードを流す）、smoke を通す。
- **Grep・Glob が読まないもの**: ルートの `.ignore`（ripgrep の決まり。Git とは関係ない）で `versions/` と生成したデータ（`god-view/data/`・`vocal-folds/js/table.js`）を外している（同じ行が何十回も当たる・1行がとても長いため）。中を探すときは、Grep の path にそのフォルダやファイルを直接わたす。生成した大きいデータを足したら `.ignore` にも足す。

## 7. 公開前チェック（つづき）

- スクリプトが調べるもの: 画像（jpg・png など）は撮影情報（Exif・GPS）や埋め込みの文字がないかを調べる（あれば止まる）。楽譜の MIDI（.mid）は中に入っている文字（曲名・トラック名など）を取り出して、MusicXML（.musicxml）はテキストとして調べる。音の WAV（.wav）は付加情報の塊（LIST/INFO・id3・bext・iXML）があれば止まる。メールアドレス、PCのユーザーフォルダのパス、APIキー・トークン・秘密鍵、パスワードの書き込み、電話番号、住所、`.env` などのファイル、`.private-words.txt` に書いた自分の語（名前・メールなど）を探す。
5. git では `.githooks/pre-commit` が同じスクリプトを自動で走らせ、見つかればコミットを止める（クローンごとに `git config core.hooksPath .githooks` が必要）。フックを飛ばす（`--no-verify`）ことはしない。
- `.private-words.txt` は PC ごとにあり、コミットされない。新しい PC では作り直す（自分の名前・メールなどを1行ずつ）。

## 7.1 内容のチェック（2026-10-15〜。`check-content.ps1`）

露出が増えるので、個人情報・秘密（`check-public.ps1`）に加えて、**中身が人に誤解・迷惑・権利の問題を起こさないか**を見る。スクリプトは候補を出すだけ。判断は目で。迷ったら公開せずユーザーに相談。

- **画面の必須**: おもな出どころ（日本語・英語）、使っているもの（ライブラリ・フォントのライセンス）、体・健康・目のアプリは「診断や治療の判断には使えない」注意書き、アクセス解析は決まった1行だけ。
- **出どころの質**: 実際に確かめた資料だけ。まとめサイト・アフィリエイト（比べるサイト・ランキング）・個人のブログ・要旨しか読めない集約サイトは、ほかに確かな資料がないときだけにし、そう書く。**特定の商品の宣伝に見える書き方・リンクにしない**。
- **外のサイト**: 新しいホストは利用条件（商用可か・キー不要か・出典の書き方）を確かめてから、スクリプトの許可リストに足す。CDN は版を固定。
- **言い切り**: 医療・健康の効き目（治る・防げる・安全）を言い切らない。誇張（世界初・完全に再現）をしない。推定・目安・演出は画面で区別する。
- **商標・作品・実在の人**: 説明のために名前を出すのはよいが、ロゴ・画像・映像・公式に見えるデザインは使わない。関係があるように見せない。実在の選手・人のデータや写真は使わない（MLB のデータの利用条件など）。
- **素材のライセンス**: 非営利だけ（CC BY-NC など）の素材・データ・API は使わない（収益化のため。自分の `LICENSE-CONTENT` の説明は別）。Wikipedia などの文・図をそのまま写さない。
- **危ないこと**: 電池・磁石・薬・毒・酒など、まねすると危ないことは「まねしない」をそばに書く。すすめる言い方にしない。
- **人**: 人を傷つける言い方・からかい・決めつけ（病気・障害・性別など）をしない。
- **AI**: 記事・動画は最後に「AI（Claude）といっしょに作った」の一文。アプリの画面で、AI が答えを出しているような誤解を作らない。
- **記事（Zenn・DEV）**: 下書きに `published_at` を書かない、アプリへのリンク（DEV は `?lang=en`）、数字はアプリの DEVNOTES と同じ。スクリプトが `../zenn/` も調べる。

## 8.1 GitHub Pages（すべてのアプリ）

- `main` ブランチのルートをそのまま配信する（`.nojekyll` あり、ルートの `index.html` が入口）。URL は `https://sishiya.github.io/manabi-lab/<app>/`。Pages の URL は公開情報なので DEVNOTES に書いてよい。
- **push した時点で公開される**。だから push の前の公開前チェック（7章）がそのまま公開前チェックになる。
- はじめから Pages 用に作ったアプリ（例: 外のデータを読む神の視点マップ）の `index.html` は普通の HTML（`<!doctype html>` から書く）。
- doctype なしで書いたアプリ（Artifact で公開していたころの形。8.2）も、Pages では互換モード（quirks）で開ける（2026-10-05 に標準モードと全要素の位置・大きさが同じことを確かめた）。**アプリを入口に移すとき**は、同じ比べ方（DEVNOTES の確認に加えて、互換モードと doctype つきの標準モードを比べる）をする。push 前にローカルで比べるときは、空の iframe に `document.write` で doctype なし・ありを書いて全要素の `getBoundingClientRect` を比べる（`iframe.srcdoc` は doctype がなくても標準モードになるので使えない。手順の例は `black-hole/DEVNOTES.md` の「公開」）。
- 外部ライブラリは、よく使うもの（2本以上のアプリ・道具の作りなおしに要るもの）はリポジトリの `lib/<名前>@<版>/` に LICENSE といっしょに置いて相対パスで読む（2026-10-12〜。いまは three.js r128 と mp4-muxer）。1本だけで大きいもの（CesiumJS など）は cdnjs・jsDelivr などの許可された CDN から、版を固定して読む。足す・版を上げるときは、ライセンスを確かめて `lib/README.md` の一覧を直す。
- 外のデータ（地図タイル・API）は、ブラウザから直接読めるもの（CORS）で、キー不要のものだけ。キーをファイルに書かない（7章）。
- **入口に載せるもの**: アプリごとに**ファビコン**（`index.html` と `launcher.html` の `<title>` の直後に、SVG を埋め込んだ `<link rel="icon" href="data:image/svg+xml,…">`。テーマ色の角丸の四角＋中身を表す図形。外のファイルにしないのは、以前の Artifact 版でも効くようにしたため）と、**サムネイル** `assets/thumbs/<app>.jpg`（640×360）。
- **保管庫**「まなびラボ 保管庫」 `archive.html`（各アプリの DEVNOTES の「隠しアーカイブ」も同じもの）: 入口の下の小さい注記からだけリンクする（`noindex`）、作りかけ・出来がいまひとつのアプリをしまっておくページ。カードは HTML に直接書く（`APPS` のような一覧は使わない）。見た目は入口に合わせ、分野でしぼる・並べかえは付けない（ユーザーが決めた）。**並びは新着順（作成日の新しい順）で、新しいカードはいちばん上に足す**。カードの形はすでにあるカードをコピーする（`.pic` の画像、`.body` に名前・説明・状態の一言 `<p class="state">`・`.foot` に `<span class="dates">作成 YYYY-MM-DD ・ 更新 YYYY-MM-DD</span>` と過去の版）。入口から外すときはカードをこちらへ移し、入口に戻すときは逆。URL を知っていれば誰でも開ける（Public リポジトリなので本当の秘密ではない）。

## 8.3 ゲームかどうかの判定と、あそびラボへの移植（2026-10-10〜）

まなびラボは「見て・ためして・しくみを知る」場所。**ゲームと判定したアプリは、姉妹サイト「あそびラボ」へ移す**。

**判定するとき**（毎回。省略しない）:
- 保管庫から入口へ移すとき（8.1。ユーザーが入口へ移すよう指示したら、移す前に判定する）
- 公開前チェック（7章）のとき。対象は公開・push するアプリ（push 全体なら、その回に中身を変えたアプリ）。一度判定して変わっていないアプリは、`GAMES.md` の判定を見るだけでよい。ただし、遊びの要素（点数・クリア・時間制限など）を足したら判定し直す。

**判定のしかた**: 次の A と B の両方に当てはめる。
- **A. 一般的なゲームの定義**（Juul 2003「The Game, the Player, the World」のゲームの6つの条件と、Salen & Zimmerman 2004『Rules of Play』の定義「ルールで決められた人工的な対立にプレイヤーが参加し、数えられる結果が出るしくみ」をもとにした）。**次の 1〜4 がすべてそろえばゲーム**:
  1. **ルール**がある（できること・できないことが決まっている）
  2. **目標と、数えられる結果**がある（勝ち／負け・クリア・点数・記録・時間など）
  3. **プレイヤーの腕前や工夫で結果が変わる**（見ているだけ・運だけで決まるものは当てはまらない）
  4. **結果に良し悪しがあり、プレイヤーがよい結果を目ざす**（うまくいった・失敗したが分かる）
  - 当てはまらない例: 決まった結果のないシミュレーションや箱庭（自由にいじって変化を見るだけ）、見るだけの展示、目標のない道具（Juul も「境界の例」としている）。
  - 学びのためのアプリでも、1〜4 がそろっていればゲームとする（教育用のゲームもゲーム）。
- **B. まなびラボ独自の基準**（ユーザーと決めたものをここに足す。A より優先する）:

## 9. 内容・文章（つづき）

- **英語対応**（2026-10-10〜）: 入口と、入口に並ぶアプリは英語でも読めるようにする（`I18N.md`。アプリは1本のまま `L(ja, en)` と `lang` 属性で切り替える）。英語対応ずみのアプリに文を足すときは、英語も同じ変更で書く。入口の `APPS` に足すアプリは `title_en`・`desc_en` も書き、アプリの中も英語にできたら `en:true`。言語（`manabi-lang`）と入口の並び順（`manabi-sort`）は `localStorage` に覚える（分野のしぼりこみは覚えない）。
- **点滅（光過敏性発作）**: 毎秒3〜30回の明るさの点滅を、画面の広い範囲に出さない（WCAG の基準: 相対輝度0.1以上の変化が毎秒3回を超える範囲を、画面のおよそ1割より小さく）。どうしても見せたいものは、選んだときだけにして、ゆれを小さくし、`prefers-reduced-motion` では出さない（例: `animal-senses` の灯りのちらつき）。点滅しそうな表現を足したら、相対輝度で測る（測り方は `wifi-wave/DEVNOTES.md` の「確認のしかた」7）。
- **使っているもの**: ライブラリ（例: Three.js＝MIT）とフォント（Google Fonts＝SIL Open Font License）を「このアプリについて」などに書く。
