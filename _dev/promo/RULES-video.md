## 8.4 紹介動画の公開前の最終確認とデバッグ（2026-10-11〜。前日に）

YouTube に予約した動画は、**公開の前日に、翌日公開の分を最終確認・デバッグする**（2026-10-11 ユーザー。直して録りなおす時間をとるため。前日にできなかったら公開の日の、遅くとも数時間前に）（ユーザーが「本日分」「明日公開分」などと言ったら、その日に公開する動画が対象。`-Verify -Date <公開日>`。予約の一覧は `_dev/promo/SCHEDULE.md`、各 `<out>.upload.json` の `publishAt`）。録ってから日がたつとアプリのほうが変わっていることがあり、動画から来た人が最初に開くのはアプリなので、**動画とアプリの両方**を見る。

1. **YouTube 側**: `youtube-upload.ps1 -Verify [-Date 日付]`（読むだけ）。処理ずみ・非公開の予約・日時・子ども向けでない・タイトル・説明・タグ・英語のタイトルと説明・英語の字幕・自分で付けたサムネイル（自動のままでないか）を JSON と突き合わせ、説明欄の URL が開けるかも見る。NG は直す（`-Update`・`-Schedule`。書きかえはユーザーの GO のあと）。
2. **動画そのもの**: 上げた mp4（`_dev/promo/out/`）を、ffmpeg で数秒おきのコマを1枚に並べて全体を見る（説明動画は約10秒おき、ショートは約3〜4秒おき）。気になるところはそこだけ細かく。見るもの: 画面が白・黒に飛ぶ／地形や絵が消える、字幕の重なり・はみ出し、名前札・年代のずれ、ライオン・しし屋の目印・締めの画面、音（無音・音割れがないか）、長さ。
3. **アプリ**: 公開中のアプリ（説明欄の URL）で `smoke.ps1 -Base https://sishiya.github.io/manabi-lab -Apps <app>,_root`。加えて、そのアプリの DEVNOTES の「確認のしかた」のうち、**動画で見せている操作・場面**を通す。
4. **不具合を見つけたら**（デバッグ）:
   - 原因がアプリなら、アプリを直す（3章のバックアップ・DEVNOTES の「状態」・「確認のしかた」を通す）。録画のときだけの問題なら台本（`_dev/promo/<台本>.html`）を直す。物理やデータを曲げて見た目を合わせない。
   - 動画が変わるときは録りなおし（`record-promo.ps1`）、古い mp4 は `<out>.before-<理由>.mp4` に残す。差しかえは、新しく上げて同じ日時で予約 → 古い方の予約を外す（`-Schedule`、publishAt なし）→ 古い方はユーザーが Studio で消す。**上げる・予約を変えるのはユーザーの GO のあと**。公開の時刻に間に合わないときは、ユーザーに伝えて公開を遅らせるか（予約を外す）そのまま出すかを決めてもらう。
   - アプリを直したら、公開前チェック（7章）→ commit。push（GitHub Pages への公開）はユーザーが頼んだときだけ。
5. **結果を残す**: `_dev/promo/upload-log.md` の「公開前の確認」の表に1行（日付・動画・結果・直したこと）。ユーザーにも伝える。残りは `_dev/TODO.md`。

## 8.5 公開前の UI/UX のブラッシュアップ（2026-10-11〜。前々日に）

紹介動画の公開の**前々日**（8.4 の前日の確認のさらに前日）に、その動画のアプリの画面を、UX デザインと認知科学をもとに**シンプルにする**（2026-10-11 ユーザー。AI で作ると情報が多すぎになりがち。ただし、これ以上へらせない情報は落とさない）。直したものは翌日の 8.4 でいっしょに確かめられる。

1. **場面ごとに、画面に出ているものを全部書き出す**（開始画面・遊んでいる最中・結果・外観など。PC 幅とスマホ幅）。
2. **1つずつ「なくしたら、何がわからなくなる・できなくなるか」を問い**、4つに分ける:
   - **いつも出す**: それがないと進めない・いまの状況がわからないもの（いまの場所、次にすること、時間など）
   - **そのときだけ出す**: 選んだ素材や状況で意味のあるときだけ（例: 日本酒のときだけ血中アルコール、危険があるときだけ危険度）
   - **詳細にしまう**: 知りたい人だけが見るもの（段階的開示。「詳細」ボタン・`details`）
   - **けずる**: 同じことを2か所で言っているもの（ボタンの状態と同じ表示など）、効いていない操作、ほぼ同じ選択肢
3. **よりどころにする考え方**: 作業記憶は一度に約4つまで（Cowan 2001）→ いつも見せる塊を少なく／選択肢が多いほど迷う（ヒックの法則）→ ほぼ同じ選択肢は1つに／段階的開示／思い出させるより見せる（ボタンに状態を出す）／近くにまとめる（ゲシュタルトの近接）／動く文字は読めない（3D に重ねた札は、その描画のカメラで位置を出し、ふるえさせない）。
4. **効いているかを測る**: ボタン・設定は、押したときに数値（進んだ距離・速さなど）が本当に変わるかをコンソールで測る。効いていなければけずる（直して効かせるかはユーザーに相談）。
5. **落とさないもの**: 9章で画面に必要なもの（注意書き・対象年齢・出どころ・使っているもの・推定と記録の区別・危険な行為の注意・法律の注意）はけずらない。場所を動かす・「詳細」にしまうのはよいが、危険の注意は最初の画面に残す。英語対応ずみなら英語も同じ変更で。
6. **動画との食いちがい**: 動画はもう録ってあるので、画面が変わったら何が変わったかをユーザーに伝える（録りなおすか、そのまま出すかはユーザーが決める。8.4 の手順）。
7. **区切り**: 3章のバックアップ・DEVNOTES の「状態」と「確認のしかた」を通す → 公開前チェック（7章）→ commit。push はユーザーが頼んだときだけ。何をけずった・しまった・残したか（と理由）をユーザーに伝える。
