# 処理の重さ（全アプリの調査と軽量化）

2026-11-01〜02。ユーザーの依頼「全アプリの処理負荷を調べて、重い処理があれば軽量化。基本はリファクタリングで、前後で挙動が変わらないことを必ず確認」。

## 測り方

- `node _dev/tools/perf.mjs [app,…]`（`_dev/tools/README.md`）。ヘッドレスの Chrome（GPU つき・1280×720）で `thumb.html` のサムネイルと同じ場面を作り、6 秒そのまま動かす。
  - **ms/秒** = メインスレッドが1秒のうち何 ms 働いたか（1000 で張りつき＝それ以上速く回せない）
  - **1コマ** = requestAnimationFrame の1回の JS の時間（平均・95%）。画面の更新の速さ（fps）にかかわらず比べられる
  - **配置＋スタイル** = レイアウトとスタイルの計算（ms/秒）。DOM を書きかえると増える
  - Worker の中と GPU の中（シェーダー）は入らない。スマホはこの数倍重いと考える。
- 前後の確かめ: `node _dev/tools/same.mjs`。乱数・時計・rAF を固定して1コマずつ進め、canvas の絵・画面の文字（DOM）・状態の配列の指紋を、変更前（HEAD）と変更後で比べる。**どの変更もビット単位で同じ**になることを確かめてから採用した（物理の計算の順番も変えていない）。
  - 例外: 実時間の setTimeout（evolution の案内が 12 秒で消える など）や、3D の最初のコマの描画は、同じコードでも実行ごとにずれることがある。ずれたときは中身を出して、変更と関係ないことを確かめた。

## 何をしたか（どれも挙動は同じ）

1. **同じ内容の DOM を書きかえない**（いちばん多かった無駄）。毎コマ `textContent`・`innerHTML`・`value`・`hidden` に同じ値を書いていて、そのたびに配置の計算がやりなおしになり、そのあとの `getBoundingClientRect`・`clientWidth` で強制的に計算させていた。内容が同じなら書かない小さな関数（`setText`/`putText`・`setHTML`/`putHTML`・`putVal`）にした。house-dust・eye-optics・metamorphosis・ga-creatures・railgun・hair-removal・sail-wind・piano-hand・typing-hand・muscle-growth・net-route・phage・spider-hunt・wave-growth、体内ダイブ3本の名札（hidden を毎秒 2600〜4200 回）。
   - `putText` は「中身が同じ文字1つだけ」のときだけ書かない（前に innerHTML で入れた太字などが残らないように）。`putHTML` は自分で入れた文字列を覚えて比べる（同じ要素へ直接 innerHTML を書く所がないことも確かめた）。
2. **場所だけで決まる計算を一度だけに**: ferrofluid の FFT の回転因子とビット反転（同じ漸化式で表に）・皿のふちの重み・3D の網目の補間の重み。縦の列の FFT は連続した配列に写して計算。
3. **同じ入力の計算を覚えておく**: spider-hunt の光の粒のゆらぎ（10ms ごとの番号が同じ間）、wave-growth の向きの広がりの係数と S(f) の分母。
4. **変わっていない所を書かない・送らない**: tiny-earth の水の柱（前と同じ高さ・色なら書かず、GPU へ送るのも書きなおした範囲だけ）。

試したがやめたもの: air-flow の圧力の反復（SOR）の係数を表にした → 速くならなかった（1つ前のマスの結果を待つ計算の連なりが律速で、表にしても変わらない）。元にもどした。evolution の名札（`labelAt`）も同じ値を書かないようにしたが、前後の差が測れなかった（211→219 ms/秒、誤差の内）ので元にもどした。

## 挙動を変えないと軽くできないもの（ユーザーと相談）

| アプリ | 重い所 | 案（どれも結果の数値や絵が少し変わる） |
|---|---|---|
| air-flow | 圧力の反復 `project()` が 6 割（1コマに最大 3 回 × 40 回の SOR）。120Hz の画面では 60Hz の2倍計算する（流れの速さが画面の速さに比例） | ① 流れの計算を「1秒に何回」で決める（画面の速さに関係なく同じ量。いまの 60Hz と同じ見た目）② 赤黒の順の SOR か Worker へ ③ 反復の回数を減らし、収束を見て打ち切る |
| ferrofluid | まだ FFT が 4 割。早送りでは1コマに最大 24 回の模様の計算 | 実数の FFT（虚部がいつも 0 なのを使う。2倍ほど速いが丸めの誤差が変わる）、Worker へ |
| wave-growth | 波の分布を作りなおすとき（風で波が育つあいだ 90ms ごと）に 1コマ 60ms 前後かかる | 半径ごとの値を覚える（向き以外は |k| だけで決まる）、Worker へ |
| piano-hand・typing-hand・chess-battle | three.js の描く回数（鍵盤・骨ごとに別の物体）。JS の 7 割が three の中 | 鍵盤をまとめた1つの物体（InstancedMesh）に。見た目は同じにできるはずだが、描く順が変わるので重なりの縁がわずかに変わりうる |
| immune-battle・weed-growth | canvas の描画そのもの（円・塗り） | 動かない部分を別の canvas に描いておく。重なり方が変わりうる |
| spider-hunt | クモの目の絵を毎コマ `getImageData` で読みもどしている | `willReadFrequently`（読みもどしが速くなるが、描き方が CPU に変わり、なめらかさがわずかに変わりうる） |

big-bang・mold-growth は別のセッションの書きかけがあったので、さわっていない。
