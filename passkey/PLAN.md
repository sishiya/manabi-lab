# パスキーのしくみ 企画書

最終更新: 2026-10-08

## ユーザーの依頼
「キーパス（＝パスキー）の仕組み・概念を理解するためのアプリを作って」（2026-10-08。KeePass ではなくパスキーと確認した）

## ねらい
パスワードの代わりに指紋・顔・PIN でログインする「パスキー」が、
- なにを・どこに・しまっていて（スマホの秘密鍵、サイトの公開鍵）
- ログインのときに、なにが行き来して
- なぜ偽サイト・データベースの流出・使い回しに強いのか

を、**自分の手で操作して、目の前で確かめる**。同じ攻撃をパスワードでも試して比べる。

ユーザーの好み（IDEAS・メモリより）: 眺めるだけでなく、さわって試せて目の前で反応するもの。本物らしさ・正確さ。出どころを画面に。

## 形
- 舞台に4人: **スマホ（認証器）**・**ブラウザ**・**サイトのサーバー**・**わるもの**。やりとりは「小包」が飛んで見える。小包を押すと中身（本物のバイト列）が見える。
- **暗号は本物**: ブラウザの Web Crypto API で、ECDSA P-256（パスキーでよく使われる ES256）の鍵を作り、署名し、検証する。秘密鍵は `extractable: false`（このアプリの JavaScript からも取り出せない）。パスワードは PBKDF2 でハッシュにする。
- サーバーの「確認リスト」（WebAuthn の仕様 §7.2 の確認）が1つずつ ✓／✗ になる。
- 操作は本物に近く: ブラウザの中のサイトのボタンを押す、スマホの指紋のところを長押し、アドレスバーでサイトを変える。
- サイト名は架空（`.example` は例のための名前。RFC 2606）: どんぐり銀行 `donguri-bank.example`、ねこ商店 `neko-shop.example`、偽サイト `donguri-bamk.example`。

## 段階A（この版）
1. パスキーを作る（登録）・ログインする
2. 実験（パスワード／パスキーを切りかえて同じ攻撃を試す）
   - 偽サイト（フィッシング）
   - サーバーのデータが盗まれた
   - 記録した返事の使い回し（リプレイ）
   - 届く途中で1バイト書きかえる（パスキーだけ）
   - スマホを落とした（パスキーだけ）
   - 2つめのサイト（サイトごとに別の鍵／パスワードの使い回し）
3. 中身を見る（バイト列を色分け、フラグのビット、ハッシュ）
4. 見つけてみよう、しくみと本当の話、おもな出どころ

## 段階B以降（案）
- 鍵の数学の小部屋（小さな楕円曲線で「かけ算は簡単・逆は難しい」を見る）
- スマホで QR を読んでパソコンにログイン（ハイブリッド）
- 同期するパスキー（新しいスマホに移る）と、デバイスに固定のパスキー（セキュリティキー）
- 本物の WebAuthn で自分の端末にパスキーを作ってみる（GitHub Pages 版だけ。端末に残るので注意書き）

## やらないこと
- 実在の会社・サービスの名前やロゴは使わない。
- 本物のパスワード・個人情報を入れさせない（パスワードは決まった例だけ）。

## 簡単にするところ（画面にも書く）
- 登録の証明書（attestation）は「なし（none）」。署名は本物では DER 形式だが、ここでは r と s を並べた 64 バイト。
- 通信はふつう TLS（https）で暗号化されている。盗み見の実験は「もし見えてしまったら」の仮定。
- 拡張機能・ユーザー名なしのログイン（discoverable credential の選択）などは省く。

## 出どころ（確かめたもの）
- W3C, Web Authentication Level 3（W3C 勧告 2026-08-25）: authenticator data の並び（rpIdHash 32 バイト・フラグ UP=bit0 UV=bit2 BE=bit3 BS=bit4 AT=bit6 ED=bit7・カウンター 4 バイト）、署名は authenticatorData ‖ SHA-256(clientDataJSON) の上、clientDataJSON の type（webauthn.create／webauthn.get）・origin・crossOrigin、チャレンジは 16 バイト以上が望ましい（§13.4.3）、秘密鍵は作った認証器から出ないのがふつう（§13.4.6）、カウンターを持たない認証器は 0 のまま。
- W3C, Web Authentication Level 2（2021）§7.2: ログインのときサーバーが確かめること。
- FIDO Alliance「Passkeys」: 同期は端末どうしで暗号化（end-to-end）、生体情報は端末から出ない、QR とハイブリッド。
- NIST SP 800-63B-4: §3.2.5 フィッシング耐性（検証者の名前に結びつける）、§3.1.1.2 パスワードはソルトつきでハッシュにして保存。
- RFC 9053（COSE のアルゴリズム、ES256 = −7）、NIST FIPS 186-5（ECDSA）、NIST SP 800-132（PBKDF2）、W3C Web Cryptography API、RFC 2606（.example）。
